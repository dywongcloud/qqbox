# 效能（繁體中文）

本頁說明 qqbox 的效能模型，並明確區分**已移除的 Go 執行期之歷史量測**與
**本 Rust 工作區目前能見證的範圍**。兩者不可混為一談。

## 改寫模型

qqbox 只改寫系統呼叫指令；其餘來賓機器碼直接在宿主 CPU 上執行，不使用動態
二元翻譯、不插入檢測程式、不啟動第二個核心。因此 slowdown 是系統呼叫密度
加上固定的每次啟動成本，而不是一個固定的倍率。改寫器不仰賴反組譯器，
以各架構專用的分類器找出 `syscall` 或 `svc` 指令的位置。

在 Linux 上，漏掉重寫的系統呼叫會觸發 seccomp 的 `RET_TRAP`，由 `SIGSYS`
處理器經 chanPage 交給 Rust 監督器服務；這是正確性的後盾，不是終止來賓。
macOS 的 Seatbelt 與 Windows 的 instrumentation callback 則會終止來賓。
這種不對稱是刻意保留的設計，詳情見
[NATIVE_BACKEND.zh-Hant.md](NATIVE_BACKEND.zh-Hant.md)。

## 歷史量測（已移除的 Go 執行期，不是本 Rust 樹）

下表中的數字來自上游 Go 執行期的基準紀錄。本 Rust 工作區**沒有**重跑這些
工作負載，也不把它們當作目前的效能承諾；Linux 後端目前只服務少量已見證的
系統呼叫，macOS 與 Windows 的來賓啟動契約尚未移植。任何 Rust 端的效能數字
都必須在即時量測之後才能宣告。

| 工作負載 | 原生 | 沙箱 | slowdown |
| --- | --- | --- | --- |
| CPU 密集（0.64 秒運算迴圈） | 0.637 秒 | 0.644 秒 | 1.01 倍 |
| 混合、典型 | 未量測 | 未量測 | 約 1.2 至 2 倍 |
| I/O 密集（64 MB，4 KB 讀取加總和） | 0.032 秒 | 0.146 秒 | 4.6 倍 |
| 系統呼叫風暴（兩百萬次 getppid） | 0.178 秒 | 0.627 秒 | 3.5 倍 |
| 啟動（noop 靜態行程） | 未量測 | 18 毫秒 | 固定成本 |

經驗法則：slowdown 約等於一加上「18 毫秒啟動成本加上系統呼叫次數乘以每次
系統呼叫額外成本」再除以原生時間。CPU 密集且長時間執行的工作約 1.0 至
1.2 倍；混合行程約 1.2 至 2 倍；小型讀寫密集約 2 至 5 倍；短於 10 毫秒的
工作由啟動成本主導；病態的系統呼叫風暴上限約 3.5 倍。每次系統呼叫的額外
成本，在 Go 執行期的量測中，簡單的模擬呼叫約 224 奈秒，4 KB 檔案讀取約
6 微秒，熱門標準輸出由 stub 直接服務而接近原生。這些同樣是歷史數字。

## 與 Docker Desktop 的比較（歷史，macOS）

在 macOS 與 Windows，Docker 把容器放進 Linux 虛擬機器；qqbox 不使用虛擬
機器，來賓在宿主 CPU 執行，監督器在宿主行程內服務系統呼叫。Go 執行期在
Apple M4、macOS 26.5、Docker Desktop 虛擬機器已暖機、映像已預先拉取的
條件下，以十五次迭代（CPU 迴圈六次）取中位數，得到：啟動 `alpine echo hi`
為 187 毫秒對 12 毫秒，啟動 Node 行程為 200 毫秒對 129 毫秒，CPU 迴圈為
559 毫秒對 525 毫秒。優勢來自啟動：沒有虛擬機器要跨越，也沒有容器要建立、
啟動與移除。CPU 密集工作接近平手，因為 Docker Desktop 的虛擬機器在 Apple
Silicon 上同樣執行接近原生的 ARM 碼。Windows 上的 Docker Desktop 是相同
架構，但當時未量測。這些數字屬於已移除的 Go 執行期，不是本 Rust 樹的
端對端證明。

## 可改善的槓桿

擴充 stub 內的快速路徑、請求批次處理、通道自旋調校，以及縮減啟動成本
（主要是靜態 libc 的一次性重寫，磁碟上的規劃快取已可跨次執行分攤）。
在 Rust 工作區中，這些都屬於設計方向的描述，尚未有即時量測背書。

## 見證範圍

`make witness` 見證控制平面的解析、接受與拒絕、以及規劃結果；
`make backend-witness` 與 `make backend-exec-elf` 在真實 Linux aarch64
核心上見證 seccomp trap、chanPage 與 Rust 監督器服務。兩者都不是效能
基準。效能必須在完整來賓執行時期可用之後，以即時量測重新建立。
