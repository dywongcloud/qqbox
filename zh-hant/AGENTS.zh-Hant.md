# qqbox 貢獻者規則（繁體中文）

> 本頁給在此儲存庫工作的代理人與人類閱讀。qqbox 是 Tencent 的沙箱：未經修改的 Linux ELF 與 OCI 容器直接在宿主 CPU 執行，沒有虛擬機器、沒有第二個核心；只有系統呼叫與同類指令被重寫並陷入監督器。Go 原始碼已移除，儲存庫是 Rust 與 Zig；控制平面是 Rust，來賓 stub 是 Zig。

## 前提：先讀懂邊界

在動手之前，先把三件事記清楚。第一，宿主端後盾是 Linux `seccomp` 的 `RET_TRAP`（`SIGSYS`）、macOS `Seatbelt`、以及 Windows instrumentation callback 搭配 `LPAC`；三者的行為不對稱，不要把它們寫成同一種結果。第二，`vfs` Namespace 是唯一的檔案系統，監督器擁有檔案與網路的資料平面。第三，原生來賓執行後端尚未移植到 Rust，因此 `cargo build --workspace` 只準備控制平面、`make witness` 只見證控制平面；從原始碼建置目前仍無法執行來賓，任何說明都必須照實陳述。以下六條規則不是風格建議，而是讓邊界維持單一、可驗證的條件。

## 規則一：只重寫系統呼叫指令

**為什麼。** 來賓機器碼必須以原生速度執行；重寫的目的不是解譯程式，而是把跨越邊界的動作集中到一處。漏改寫的呼叫由宿主後盾接住：Linux 以 `SIGSYS` 把呼叫導回監督器，macOS 與 Windows 的後盾則阻止繼續執行。若為了方便而偷偷加一條繞過重寫器的模擬路徑，等於把邊界拆成兩份，將來必定有一份漏掉，而這類錯誤通常要等到對抗式驗證才會浮現。

**如何套用。** 只修改 `syscall`／`svc` 一類指令所在的位元組，其餘位元組原封不動。找到漏網位置時，修正分類器並把該位置納入語料，不要引入完整反組譯器當作萬靈丹，也不要把失敗靜默轉成成功。每個新的陷入點都要能回答：它對應哪一個宿主後盾、漏掉時會發生什麼事。

## 規則二：`vfs` Namespace 是唯一的檔案系統

**為什麼。** 只要有任何一條路徑不經過 `vfs`，來賓就能用宿主路徑讀取或寫入不該碰的檔案，隔離立刻破功。合成檔案系統與實際掛載必須是同質物件；一旦為特定工作負載開特例，特例就會長成後門，且難以用單一見證覆蓋。

**如何套用。** 所有路徑解析（含 `..`、絕對符號連結、`O_PATH` 與 magic link）都走同一個 Namespace；`mount`、bind、`pivot_root`、overlay、`/proc`、`/sys`、`/dev` 與 cgroup 樹都是 Namespace 操作；系統呼叫處理常式不得直接取用宿主路徑；裝置節點只能來自固定允許清單。遇到難解的路徑語意，請在 `vfs` 內一般性地做對，比照真實 Linux 行為，不要替單一工作負載開快捷徑。

## 規則三：監督器擁有資料平面

**為什麼。** 把檔案與網路的資料平面放進來賓 stub，等於讓能寫入 stub 每一個位元組的來賓自行決定 I/O 結果；監督器也無從套用 `:53` DNS 攔截、對外允許清單與檔案權限。隔離的判決點必須留在來賓改不到的地方。

**如何套用。** Zig stub 只做必須留在來賓位址空間的事：執行緒控制、訊號跳板、標準輸出入的快速路徑。檔案的讀取、寫入、開啟、關閉，以及 `connect()`、DNS 解析與 TCP 代理，都由 Rust 監督器執行，來賓只轉送請求。效能改進請從更便宜的通道、批次與快速路徑著手，不要把資料平面搬進 stub；也不要為了讓某個範例跑得快一點而放寬宿主端過濾器。

## 規則四：來賓原生程式碼是 Zig，監督器與控制平面是 Rust

**為什麼。** 兩層的信任邊界與工具鏈不同。freestanding stub 不能連結 libc；控制平面需要型別、錯誤處理、以及「接受或附診斷訊息拒絕」的能力。混用會讓共享通道的版面偏移而無人察覺，錯誤會以最難重現的方式出現。

**如何套用。** 所有 stub 與原生輔助程式都以 Zig 撰寫，不使用 C；監督器、CLI `qqbox`、常駐程式 `qqboxd`，以及 OCI、Compose、`vfs`、重寫與網路政策的規劃，都以 Rust 撰寫，位於 `crates/qqbox`、`crates/qqbox-cli`、`crates/qqboxd`。共享通道的版面必須兩端位元組一致，任何更動都同時驗證並以 `make witness` 留下見證。程式識別字、旗標與路徑維持拉丁原文；由 laboon 更名為 qqbox 不應偷偷改動 ABI，更不能把更名當作後端已經移植完成的證據。

## 規則五：程式庫接受選項，不讀環境變數

**為什麼。** 環境變數是隱藏的全域輸入，會讓同一份程式庫在不同宿主上行為不同，也讓對抗式驗證無法重現。政策應該是呼叫者明確給予的，而不是從宿主空氣中飄進來的；這也是「零信任」在程式庫層的含意。

**如何套用。** 行為一律由 `Options`／`Config` 之類的選項帶入；只有可執行檔、範例與測試工具可以讀環境。`-net` 是明確的開關，`-allow-domains`、`-allow-cidrs`、`-allow-ports` 只用來收緊，不會放寬 `-net`，也不會授予新權限。不要用環境變數偷偷開啟對外連線，不要新增全域變數當作政策來源，也不要把安全相關的預設值藏在條件編譯裡。

## 規則六：絕不以 `sleep`、timeout 或週期性重查當作正確性的修正

**為什麼。** 等待一段時間不會讓競態消失，只會把錯誤搬到更少出現的時序；這類修正把見證變成機率遊戲，也把真正的同步缺陷藏起來。延遲有時能讓紅燈變綠，但那不是證據，只是運氣。

**如何套用。** 以取消、事件、條件變數或明確的狀態機同步；移除既有程式裡的定時重查；不要用注入延遲來「重現」競態。必要時以 `make witness` 的輸出與對抗式驗證的記錄與證據證明修正，並說清楚它屬於控制平面的接受／拒絕結果，還是來賓執行的端對端證明；目前的工作區只能給出前者。

## 在這個儲存庫工作

- 建置入口是 `cargo build --workspace`，見證是 `make witness`；兩者都屬於控制平面。
- 誠實邊界：Linux memfd／`seccomp`／hop、macOS Mach／`Seatbelt`／HVF、Windows `LPAC` 三組原生後端尚未移植到 Rust，Go 原始碼已移除。從原始碼建置只能準備控制平面，不能執行來賓；不要在說明文件、註解或提交訊息裡把這件事寫成「已可執行」。
- 變更若影響多個宿主，先閘住該項目，再跑完整語料；不要用未經見證的宣稱填補空白。
- 註解保持精簡，程式碼本身要能讀懂。不要在程式碼、註解或提交訊息裡標註工具或模式名稱。
